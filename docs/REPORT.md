## 二、系统设计

### 2.1 技术结构

- **Python**：实现后端业务逻辑。
- **FastAPI**：提供 HTTP API、请求参数校验和 OpenAPI 文档。
- **PyMongo**：连接 MongoDB 并执行数据读写。
- **MongoDB**：保存用户、问卷、答卷和会话数据。
- **原生 HTML/CSS/JavaScript**：提供问卷管理、填写、跳转及统计页面，不依赖 CDN。
- **pytest**：执行自动化测试；另有 Playwright 与无界面 Microsoft Edge 的浏览器流程测试。

### 2.2 主要调用关系

```text
浏览器页面（HTML/CSS/JavaScript）
             |
             | HTTP / JSON
             v
        FastAPI 路由
             |
     +-------+---------+----------------+
     |                 |                |
  认证与权限        问卷/题目逻辑      答卷/统计逻辑
  auth.py           surveys.py         responses.py
                    questions.py       statistics.py
                    logic.py
             |
             v
           PyMongo
             |
             v
           MongoDB
  users / surveys / responses / sessions
```

模块划分使认证、问卷生命周期、题目校验、跳转、答卷保存和统计逻辑相对独立。第二阶段可以在保留现有接口和数据模型的基础上修改受影响模块，并增加迁移和回归测试，而不是重新实现整个系统。

## 三、MongoDB 设计

数据库默认名为 `survey_system`，可通过 `MONGODB_DATABASE` 配置；连接地址由 `MONGODB_URI` 配置。项目不使用关系数据库，也没有用内存数据库替代 MongoDB。

### 3.1 集合设计

| 集合 | 主要字段 | 作用与索引 |
|---|---|---|
| `users` | `_id`、`username`、`salt`、`password_hash`、`created_at` | 保存用户资料；用户名唯一索引防止重复注册 |
| `surveys` | `_id`、`owner_id`、标题、说明、匿名设置、状态、截止时间、`questions`、`revision`、`schema_version` | 保存问卷及其题目；`owner_id` 索引用于查询用户自己的问卷 |
| `responses` | `_id`、`survey_id`、`respondent_id`、`answers`、`path`、`created_at`、`schema_version`、可选 `once_key` | 每次成功提交形成一份独立答卷；按问卷 ID 查询统计；部分唯一索引支持限制每人填写一次 |
| `sessions` | `_id`、`user_id`、`expires_at` | 保存会话令牌摘要和有效期；TTL 索引清理过期会话 |

### 3.2 嵌入与引用

问卷的题目、选项、校验配置和跳转规则嵌入 `surveys` 文档。这样读取问卷时可以一次获得完整结构，题目与规则也能在草稿状态下作为一个问卷整体维护。题目有稳定 ID，答案通过题目 ID 关联，不依赖题目当前所在位置。

用户和答卷分开存储。答卷数量会随着提交增长，如果将所有答卷嵌入问卷文档，会使问卷文档不断膨胀；因此答卷放在独立的 `responses` 集合，通过 `survey_id` 关联问卷。用户和会话也分别存储，避免重复保存用户资料。

这种设计利用 MongoDB 文档与数组表达不同题型的结构，同时保留必要的 ID 引用。没有照搬关系数据库中题目、选项、规则等多层关联表的结构。当前由 Pydantic 和业务函数校验 API 写入数据，尚未设置 MongoDB 原生 `$jsonSchema` 校验；直接使用数据库管理工具写入的数据不属于 API 校验保障范围。

### 3.3 数据与隐私边界

密码以随机盐和 PBKDF2-HMAC-SHA256 哈希形式保存，不保存明文密码。会话令牌原文由浏览器保存于 `sessionStorage`，数据库存储令牌的 SHA-256 摘要。时间按 UTC 保存。

匿名问卷仍要求填写者登录。数据库内部保留 `respondent_id`，以便限制同一用户重复填写；问卷创建者通过答卷详情和统计接口无法直接获得匿名填写者身份。匿名并不意味着数据库管理员无法追溯，填写者也可能在自由文本答案中主动透露身份。

## 四、跳转与校验设计

### 4.1 跳转规则

跳转规则由问卷创建者配置并存储在 MongoDB 中，不写死在程序里。系统支持：

- 单选题：`eq`，比较所选选项 ID。
- 多选题：`contains_any`（至少命中一个指定选项）和 `contains_all`（指定选项全部被选中）。
- 数字填空：`eq`、`gt`、`gte`、`lt`、`lte`。
- 跳转目标：后续题目的 ID 或 `END`。

规则按数组顺序检查，第一条匹配规则生效；没有规则匹配时进入下一题，最后一题默认结束。目标必须位于当前题之后或为 `END`，所以正常跳转不会回到前面的题目，也不会形成循环。前向跳转是本项目的明确限制，不支持回跳。

示例规则：

```json
{
  "rules": [
    {"op": "lt", "value": 18, "target": "后续题目ID"},
    {"op": "gte", "value": 18, "target": "END"}
  ]
}
```

数字小于 18 时跳转到指定的后续题目，否则结束问卷。实际配置中的 `target` 必须替换为问卷中真实存在的后续题目 ID。

### 4.2 答案校验

服务端是最终校验方，不能仅依赖浏览器校验。选择题检查选项 ID、重复选项和多选数量限制；文本题检查必答、空白内容及最小/最大字符数；数字题拒绝字符串、布尔值和非有限数字，并检查最小值、最大值及整数条件。

填写过程由服务端根据答案重新计算路径。只校验实际经过的题目，因此被跳转规则跳过的必答题不要求回答。提交时服务端从第一题重新计算完整路径，并拒绝未知题目或路径之外的额外答案，不能只相信客户端传来的路径。

## 五、身份、问卷生命周期与匿名设计

用户注册后登录，服务端生成有有效期的会话令牌。管理和统计接口均执行用户身份与问卷所有权检查，访问其他用户的问卷按未找到处理，避免通过猜测 URL 读取管理数据。

问卷生命周期为 `draft → published → closed`。草稿可修改，发布前要求问卷至少有一道题并通过结构检查。发布后冻结题目与规则，避免历史答卷与后续题目结构不一致；关闭后不能重新开启。截止时间到达后，填写接口拒绝新提交。

禁止重复填写时，系统为答卷生成 `once_key`，由 MongoDB 部分唯一索引处理并发重复提交；允许多次填写时不设置该键，每次成功提交均形成独立答卷。匿名设置控制的是创建者可见的身份信息，不会删除数据库内部的用户关联。

## 八、遇到的问题、处理与已知限制

### 8.1 已记录的问题与处理

1. **Word 需求文件读取时被占用。** 现有日志记录使用共享只读方式提取正文，没有修改原始需求文件。
2. **执行环境最初无法连接本机数据库。** 现有日志记录在获得执行环境授权后，使用本机真实 MongoDB 完成测试。
3. **项目环境最初缺少依赖。** 在项目独立虚拟环境中安装依赖，避免将依赖安装到系统 Python。
4. **测试时间精度比较失败。** 首轮测试将微秒级创建响应与 MongoDB 毫秒精度读取结果进行全对象比较；随后只修正测试的时间精度预期，业务代码保持不变，单例及全套测试通过。

### 8.2 当前已知限制

- 仅在成功提交后保存整份答卷；未提交内容不会自动保存，刷新页面可能丢失填写内容。
- 跳转只允许向后，不支持回跳。
- 问卷关闭后不能重新开启。
- 统计目前将答卷载入内存计算，没有分页，适合课堂规模数据。
- 关闭问卷与答卷插入不是跨文档事务；已经通过检查且正在执行的提交可能在关闭后完成写入。
- 匿名仅对问卷创建者隐藏身份，数据库管理员仍可看到内部关联。
- 运行范围是本机课堂演示，没有实现互联网部署、邮件通知、找回密码、答卷导出、删除问卷或服务端草稿自动保存。

这些限制已在 `docs/LOGIC.md` 中说明。
