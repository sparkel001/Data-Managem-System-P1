### L01 项目检查与基础环境

> 先检查当前工作区和已有文件，不要覆盖无关文件。按阶段实现，每阶段运行测试并汇报结果：
>
> BLOCK 1：搭建项目结构、配置管理、MongoDB 连接、健康检查接口和运行说明。

开发首先从工作区和课程要求检查开始。项目在新建的 `survey_system/` 目录中组织，生成 `app/config.py`、`app/main.py`、`.env.example`、`pytest.ini`、测试数据库夹具和健康检查测试，并编写初版 README。该阶段完成环境变量配置、MongoDB 连接管理及 `/api/health` 接口。

读取课程 Word 文件时遇到占用错误，随后调整为共享只读方式提取正文。运行依赖安装在项目独立虚拟环境中；本机数据库连接受执行环境限制，经环境授权后验证成功。此阶段未修改原始课程文档。

阶段测试结果为 **1 通过、0 失败**，健康检查实际连接本机 MongoDB。

### L02 注册登录与问卷所有权

> BLOCK 2：实现注册登录、密码哈希、当前用户身份校验，以及用户只能访问自己创建的问卷。

生成的 `app/auth.py` 实现注册、登录、退出、当前用户查询及 `owned()` 所有权检查。密码使用随机盐和 PBKDF2-HMAC-SHA256 处理；会话信息保存在 MongoDB，令牌原文不直接写入数据库。

在此基础上，`app/main.py` 增加认证路由、用户名唯一索引和会话 TTL 索引，`tests/test_block2.py` 检查错误密码、重复注册、退出失效及问卷访问限制。累计测试结果为 **3 通过、0 失败**。

### L03 问卷创建与状态管理

> BLOCK 3：实现问卷创建、编辑、发布、关闭、设置截止时间和问卷分享链接。

`app/surveys.py` 提供创建、列表、详情、草稿编辑、发布和关闭接口，并生成问卷分享路径。截止时间必须包含时区；状态按 `draft → published → closed` 转移。

为保持历史答卷与题目结构一致，生成方案规定发布后冻结设置和结构。草稿更新增加 `revision` 条件，以识别并发修改冲突。管理接口同时接入所有权检查。

`tests/test_block3.py` 完成后累计 **5 通过、0 失败**。其中部分生命周期测试直接在测试库插入占位题，尚不足以证明添加题目接口的完整性；这一缺口在后续审计中单独处理。

### L04 四类题目及答案校验

> BLOCK 4：支持单选、多选、文本填空、数字填空；校验必答、选择数量、文本长度、数字范围和整数要求。

生成 `app/questions.py`，以 `QuestionInput` 描述题目配置，由 `validate_answer()` 检查实际答案。题目采用稳定 UUID，选择题选项使用独立 ID；文本和数字题分别保存长度、范围及整数约束。

题目配置增加上下限及选项 ID 唯一性检查，编辑时保留原题目 ID。`tests/test_block4.py` 验证题目添加、编辑和主要校验条件，累计 **19 通过、0 失败**。此时部分校验仍以内部函数测试为主，提交接口层面的边界与落库检查在 L11 补充。

### L05 可配置跳转规则

> BLOCK 5：实现可配置跳转规则，规则存储在 MongoDB 中，不写死在程序里。支持单选、多选和数字答案触发跳转；检查目标题目存在，避免跳转循环或无法结束。

`app/logic.py` 实现规则检查、条件匹配和路径执行，主要函数包括 `validate_rules()`、`matches()`、`next_id()` 和 `walk()`。规则作为题目文档中的数组写入 MongoDB。单选使用 `eq`，多选使用 `contains_any` 或 `contains_all`，数字题使用相应比较运算。

生成方案将跳转目标限定为后续题目或 `END`，通过题目序号递增保证路径能够结束。多条规则按顺序匹配，首个匹配项生效；题目编辑与发布流程也增加规则复核。

`tests/test_block5.py` 覆盖三类触发、自跳和不存在目标、规则保存及路径外答案拒绝，累计 **26 通过、0 失败**。

### L06 填写提交与演示网页

> 技术选型：Python、FastAPI、MongoDB、简单 HTML/CSS/JavaScript。
>
> BLOCK 6：实现问卷填写、提交和保存；支持同一用户多次填写的配置。匿名问卷仍要求填写者登录，但统计和答卷详情中不向创建者展示填写者身份，请在文档中说明。

生成 `app/responses.py` 及 `app/static/` 下的 HTML、CSS 和 JavaScript，提供账号、管理、规则配置、逐题填写和统计页面。提交时由服务端重新计算路径，并按问卷 ID 和题目 ID 保存答案。

匿名答卷内部保留用户关联，创建者详情接口通过字段白名单隐藏身份。限制每人一次时，使用 `once_key` 部分唯一索引处理重复提交；允许多次时，每次有效提交形成独立答卷。应用入口相应增加静态资源和页面路由。

该阶段累计 **30 通过、0 失败**，JavaScript 语法检查通过。当时完成的是网页路由与语法检查，实际浏览器流程在 L08 中验证。

### L07 整卷与单题统计

> BLOCK 7：实现问卷统计：单选各选项人数、多选各选项次数、总答卷数、填空答案列表、数字平均值，以及单题统计接口。

`app/statistics.py` 实现整卷和单题统计接口，使用 `summarize()` 从已保存答卷中计算选项计数、回答数、填空列表及数字均值。无数字答案时均值返回 `null`；允许多次填写时按有效答卷计数。

应用路由接入统计模块，前端统计页面调用相应接口。`tests/test_block7.py` 检查四类整卷结果、数字单题、空数据和统计访问权限，累计 **31 通过、0 失败**。

### L12 时间精度问题与复测

> 不要为了让测试通过而静默修改业务代码；如果发现代码问题，先说明问题和涉及文件。

AI 先在对话中报告失败数、原因和涉及文件，再调整 `tests/test_course_requirements.py`：将创建时间截断到毫秒，与数据库及读取时间比较；同时要求原始时间差小于一毫秒，其他字段继续严格比较。业务响应位置为 `app/surveys.py`，本轮未对其作修改。业务文件 SHA-256 对照结果一致。

## 5.2 AI 使用说明

### AI 完成的工作

AI 承担了本项目主要代码实现与自动化验证工作，包括后端模块、MongoDB 文档结构、接口、原生网页、测试及配套说明。问卷、题目和跳转规则通过嵌入文档表达，答卷通过稳定 ID 关联；用户、答卷和会话分别存储，避免将全部数据集中在单个集合。

开发交付后，AI 又按新的验收要求复核六类测试，补充原有断言未充分覆盖的接口场景，并生成逐项用例记录。最终测试结果能够对应到具体文件、输入和断言，而不仅是一个通过总数。

| 工作内容 | 主要产物 |
| --- | --- |
| 后端与数据库访问 | `app/` 下的配置、认证、问卷、题目、跳转、答卷及统计模块 |
| 网页与离线接口文档 | `app/static/` |
| 数据库建模说明 | `docs/DATABASE.md`、索引创建逻辑 |
| 自动化验证与结果采集 | `tests/`、`scripts/build_test_audit_docs.py` |
| 运行与交付文档 | README、API、逻辑说明、测试记录和报告模板 |

### 出现的问题及改进

最明确的错误是时间精度测试。AI 忽略 BSON Date 的毫秒精度，用全对象相等判断创建和读取结果，产生了一个本不应据此判定保存失败的测试。修正限于测试预期，并保留了时间差约束及其他字段的严格比较。首轮失败、单例复测和全套复测均有证据可查。

初版测试也有覆盖不足。43 项通过能够说明已有断言成立，但不能证明六类课程要求的全部关键场景均已验证。后续检查发现，部分测试只调用内部函数，或直接向测试库写入占位题，因此补充了通过真实 API 执行并检查数据库结果的场景。

文件占用和数据库连接限制则属于环境处理问题。读取方式和执行权限调整后，相关操作能够继续，原需求文件及开发业务数据未因此被覆盖。

系统仍保留明确的第一阶段范围：未提交内容不自动保存，跳转仅向后，发布后结构冻结，统计面向课堂规模而未分页。这些限制已写入项目说明，不能由测试通过推导为具备相应扩展能力。

本项目通过明确需求、分阶段生成、执行测试和复核证据的方式使用 AI。AI 提高了代码与文档的形成效率，但生成结果仍需逐项验证。时间精度失败表明，测试本身也可能存在错误；初版覆盖不足则说明，通过数量不能替代对需求和断言的核对。
